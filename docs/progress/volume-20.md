### The rules

**The allowance owes the history a floor it can refuse.** `R15`: an allowance under twice the slowest
*whole* prefix any recording holds is a day the budget has already refused for being slow. Twice,
because it is the multiple `R4` asks of a work step. The rule binds at 90 seconds -- 180 is exactly
twice 90, and a 91-second prefix raises the requirement to four minutes. A row counts only when it
measured every step of the prefix: a history missing one setup step sums to less than the prefix cost,
and that is the hole `jobDays` refuses one level up.

**A clause owes an address and a round.** An address is something a reader can open -- a finding, a
falsification table, a run id, or a test file. A test file counts because it *is* the case: whoever
opens `publish.test.ts` sees the three shapes the created-branch clause describes. The rule exists
because the alternative is a judgement with no case, which is a preference, which is what finding 121
refused in prose.

**The index is a projection, compared line by line.** One row per clause, its heading and its round,
regenerated by `--write` and refused when a row is missing, extra, out of order, or says heading text
the file no longer says. It carries **no links**: a GitHub anchor is a slug this script would compute
by guessing, and a slug one character off is a link that fails silently -- finding 621's shape, one
document over.

### Why the previous round's number was wrong

v3.133 classified a bullet as "provenance" when it matched one of seven patterns, and reported **125**
rules against **92** recollections. The first section it misread decides the question: `The two
sentences in one entry (v3.63)` is three bullets, all three of them rules, all three citing something.
A real reader would call them judgements; the heuristic called them recollections and left the section
with no rule at all.

So the file is not "rules plus a chronicle". It is case law, and what case law owes is not a shorter
page but an address per judgement and a way to find one. That is what this round built, and the
length is what it costs -- `O-019`'s complaint was navigation, not length, and the index is the repair.

### The measurement

`coincidencesOf` classified an equality by whether one declared population held the gates that printed

| --- | --- | --- | --- |
| one declared population holds every one of them | a rule, and the run checks it | yes, and it does | **3** |
| every gate placed, no population holds them all | a **size** between sets the record says differ | no -- a size is not a claim | **1** |
| at least one gate nobody has placed | the only evidence they might be one set | no -- the question is open | **0** |

Before this round the line said `4 count(s) coincide across gates -- 3 inside a declared population and
1 across two`, and the `1 across two` was `8 row(s)`: two gates the record places in populations of

The `0` in the third class is printed rather than omitted. That is the whole of the answer to the
entry's second half: a size is not a claim, so nothing can be refused when it moves -- but the class can
be **counted**, and then a coincidence that goes out is a number that moves rather than a clause that
vanishes.

### Three answers that were possible

**Refuse a coincidence between two populations of one.** It reads as the strict answer and it is
arithmetic: the populations are a person's claim about sets, the coincidence is a property of two
integers. A rule that refused it would fire the first time two unrelated tables held the same number of
rows, and the repair would be to change a table.

**Drop the `apart` ones.** Cheapest, and it is finding 611: a reader that stops counting a number it
read, so the next reader cannot tell a coincidence that went out from a census that stopped looking.

**Classify, and count all three.** Taken. `together`, `apart`, `unplaced`; a gate declared `separate` is
placed, and placed as something that is not a population, because its number is not a count of the noun.

## v3.137 — a marker names the count it is about, and a snapshot is a claim about a tree

Two entries this round, both of them a sentence that was true of one thing and read as a statement
about another. `O-107` was opened by v3.136's own repair: the marker had just been given its three
classes and still spoke once for a noun that can carry two equalities. `O-103` was opened two rounds
earlier by a snapshot taken in the middle of a round's edits, and it asks a question no writer can
answer.

### The marker spoke for the noun

`O-107`'s own text named the cost and the counter-argument: *eight characters per coincidence, and a
list once a noun has three*, against *a marker that speaks for the noun is the right granularity
precisely because the numbers line has already spoken for each count*. Both halves are true, and the
second one is what the line did -- once per noun, first branch that matched.

The state it could not express is one census row away. Four gates, `8` printed by `a` and `b` inside a
declared population and `9` printed by `c` and `d` from populations of their own:

```
row(s) — 8 in a; 8 in b (one population at 8, and the count agrees); 9 in c; 9 in d
(at 9, a count two gates print agrees, and the record places them in different sets) — four tables
```

The old line printed the second parenthesis without `at 9`, once, for the noun -- true of the `9`,
false of the `8` four words earlier. A reader who acted on it acted on the number it was not about,
which is finding 611 one turn further out: a sentence that reaches the right verdict about the wrong
subject.

The repair is one sentence per coincidence, built from that coincidence:

```js
const what =
  one.placement === 'unplaced'
    ? 'a count two gates print agrees, and no population places them'
    : one.placement === 'apart'
      ? 'a count two gates print agrees, and the record places them in different sets'
      : null;
if (what !== null) said.push(`at ${String(one.count)}, ${what}`);
```

The class that needs no marker still contributes none, and the old argument -- `unplaced` holds only
for an undeclared noun, `apart` only for a declared one, so the two can never co-occur -- is still true
and no longer load bearing. v3.136 called the joined-list shape *dead before it ran once*; what was dead
was the branch that joined **classes**, and the shape that survives joins **coincidences**, of which a
noun may have several of one class. The comment says so, and the fixture that proves it prints `at 3`
and `at 12` under one noun.

### The reader that can refuse a snapshot

## v3.141 — the middle of every bound, and the floor under a range

### The middle of every bound

`O-116` printed the middle for the tightest bound because that is the multiple the sentence asks a

and the shipped tree says so: the bound nearest a **bad** day is `backend / Install a backend this
repository did not write` at `2.0x` (1800 s over 888 s), and the bound nearest a **usual** day is
`batteries-heavy / Backend-support battery` at `2.4x` (900 s over 382 s). Two bounds, two capacity
questions, and only the first had a middle printed.

The population is **38** bounds, **36** of which have a command whose middle is above 0 s; the other
**2** divide by a middle of 0 s, where no multiple exists. Printing thirty-six middles would be a table

Both ends are an extreme of one set rather than a choice, which is what makes this a rule: the figure

The first verb was `run`, and this file spends `run` on a workflow run in twenty clauses, so `the 36

### The floor under the range

`O-114` said the range over the history mixes the tree's growth with the runner's variance, and that
only a re-run of one commit separates them -- a pair the history did not hold, because every reading
was of a different commit. So this round made one: run `45351350110` was re-run, which GitHub records
as **attempt 2 of the same run id**, and both attempts were recorded.

`noiseFloorOf` compares every **pair** of readings of one commit rather than the neighbouring ones,
because with one tree read three times the widest difference is between the first and the third; a step
only one of the two readings timed has no difference to take; and `null` is returned when no two
readings share a tree, so the sentence says in words that the floor has not been measured rather than
leaving a silence to be read as a floor of zero.

### A run id was the identity of a reading

The measurement could not be written down, and the three reasons were one reason:

```js
if (seen.has(run)) {              // readReadings: attempt 2 refused as a duplicate
if (one?.run !== entry.run) ...   // mergeReading: attempt 1 silently replaced
const jobs = await get(`/actions/runs/${RUN}/jobs?per_page=100`);  // the recorder: latest only
```

A re-run keeps the run id and increments `run_attempt`, so the identity of a reading is the
measurement, not the id. `readReadings` keys by `run#attempt` and refuses an attempt that is not a
positive integer; `mergeReading` replaces one attempt and keeps the other; `R10`'s two directions
compare the pair `(run, attempt)`, so a history that stops at attempt 1 while the recording is attempt
2 is refused as a reading that was taken and not written down; the recorder reads `run_attempt`, writes
it into both files, and takes `--attempt <n>` to record an older one, which is the only call that asks
the API for `filter=all`.

An absent `attempt` is **1**, which is what every recording written before the field existed was: the
thirty-one readings already in the file are unchanged and still valid, and the recording became the
pair's second attempt with no migration.

A duplicated reading is therefore neither a second day nor a second number on its own. It is a second
measurement of one tree: it stays in the series `R10` divides by and in the middle, because a bound has
to survive every measurement of it, and it is printed as the floor rather than counted as another tree.

## v3.142 · Every round states its own size twice, and only one of the two statements had a reader

## v3.143 — a bound's margin in the machine's own movement, and a reading named by two fields

### The arithmetic, which closes the first half of the question

## v3.144 — the recorder decided older and newer on the run id, and wrote the tree its gate refuses

`O-122` recorded a state rather than a mistake: `--attempt 1` after `--attempt 2` of one run was
accepted, the recording moved backwards, and `R10` refused the tree the recorder had just written. The
round answered both of the entry's questions, found that the same comparison had two more shapes
behind it, and left one new entry where the answers stop.

### What the write did to the two files

| step | `ci-baseline.json` | `ci-readings.json` |
| --- | --- | --- |
| before | `(7, 2)` | `… (7, 2)` |
| `--attempt 1` | `(7, 1)` -- rewritten | `… (7, 1), (7, 2)` -- appended and **sorted**, so the tail is still `(7, 2)` |
| `R10` next | older than the history's tail | "the history holds a reading of run 7 attempt 2, which is newer than the recording (run 7)" |

The refusal is right and its advice is not: "record that run as the recording rather than beside it"
names the act the recorder had just been asked to take.

### The two questions, and why the second dissolves

Whether the recorder should refuse an older attempt is not policy. `R10` compares the recording with
the history's **tail**, and the tail is a maximum over the file, so no write of `ci-baseline.json`
alone can move it; an older attempt could only be the recording if the newer row left the history, and
the only way to remove a row is the hand edit both files refuse in the same words. So the repair the
entry was reaching for -- "the latest attempt was red" -- is not reachable by moving the recording. It
is reachable by the other relation: the older attempt's seconds go into the **history**, where `R10`'s
denominator reads them, while the recording stays on the newest measurement.

Whether the recording holds the newest attempt by measurement time or by attempt number is not a
question the file has to answer: a re-run of one tree increments `run_attempt`, so attempt `N + 1` was
measured after attempt `N`, and the two orders are one order. The pair *is* the order.

### The same comparison had a second shape, and it was hiding the noise floor

The seed's relation to the recording was decided by subtracting run ids, so `--seed --attempt 1` of
the recorded run was refused as "the recording", in a sentence about one day entered twice. It is not
one day. It is a second measurement of one tree -- the pair `v3.143` had just measured every bound's
margin against -- and the history already holds one:

| run | attempt | commit | `batteries-heavy / Type-miss probe battery` |
| --- | --- | --- | --- |
| `45351350110` | 1 | `45eaacff` | 356 s |
| `45351350110` | 2 | `45eaacff` | 507 s |

What the recorder could not do is append a second one for the run that *is* the recording.

### The third shape: the file that says which day is the newest, overwritten

`if (!SEED) writeFileSync(OUT, …)` ran whatever was already at `OUT`. For a recording that could not
be parsed, that is an unanswerable question answered by deleting it: the history keeps the newer day,
and the tree fails with `R10`'s advice about a recording the recorder had just written. It is refused
now in two shapes -- a file that does not parse, and a file that parses into something naming no run
-- each with the act that fixes it. The two files were asymmetric before this round: a history that
cannot be read was left alone and reported, and the recording was overwritten in silence.

### One ordering, one name

## v3.145 — a number the run did not measure, and the bound `R4` then asked to be doubled

`O-127` recorded two states: the recorder recorded a run that failed, and a step that expired spent exactly

at least twice the number beside it, which is an argument only when that number is a duration the command
spent; a step killed at its bound reports the bound, so the rule compared a bound with itself and advised

| a step stopped early (`cancelled`) | a lower bound on the command | a small bound, which every rule passes |
| a run that failed | the later steps never ran | a bound per step of a job the run did not finish |

## v3.146 — the bound a red day enforced, and the one it did not

`v3.145` closed `O-127` and left `O-128` standing with two routes: read `ci.yml` at the seed's `head_sha`,
or keep only `success` steps. The round took the first and refused the second, and the refusal is the
argument the round is built on.

### One conclusion, two shapes, and the field that does not separate them

`O-127` said a `failure` step of a seed is kept "because a command that ran and returned non-zero spent that
long". The first half is true and the second is only sometimes:

| the shape | what the number is | what `R10` then divides by |
| --- | --- | --- |
| the command ran to its end and returned non-zero | a duration | the worst day of the command, which is what the rule means |
| the runner stopped the step at its own `timeout-minutes` | the bound in force that day | a bound, so the multiple asks for a bound twice the number the run was killed by |

Why the second route was refused: a seed exists to keep a **red** day's numbers, because `R10`'s denominator
is the worst day rather than the greenest one. Keeping only `success` steps would delete exactly the days
the rule was written for, and would do it silently -- the file would look healthy with its slow rows gone.

### The arithmetic was right and the number in it was today's

`O-127`'s separation of a duration from a bound is *a step that ends on its own ends before its bound*, so
`seconds >= bound` means the number is that bound. The inequality is an argument only when `bound` is the
number the runner was enforcing. A seed's day is not today: `ci.yml` states today's bound, and that day's
`ci.yml` stated the one that killed the step.

So the recorder reads that day's file -- `GET /contents/.github/workflows/ci.yml?ref=<head_sha>`, walked by
the same line reader the gate uses on today's -- and holds each `failure` step to the bound it states:

| what that day says about the step | what the recorder does | why |
| --- | --- | --- |
| bounded at `N`, and the step spent at least `N * 60` s | drops it, naming `N` and *that day* | the number is that bound read back |
| bounded nowhere | keeps it | the job timeout cancels the running step rather than failing it, and a cancelled step is already dropped -- no step bound can have stopped this one |
| no such job in that day's workflow | drops it, saying which fact it is | the step may have run under a bound this reader cannot find, so the number cannot be proved a duration |
| the file cannot be read at all | refuses the seed | the question is open; a seed that answered it by guessing would append a day with its slow steps missing |

The last row is why the middle ones are not a compromise. The rule is not "keep what we cannot disprove",
it is "ask the day, and refuse when the day cannot answer". A refusal is a state a reader can act on.

### The cost, and who pays it

One request per seed, and only when the run holds a step the API called `failure` -- which a green run never
holds, because GitHub computes a run's conclusion from its steps. A seed of a green day costs what it always
did; the price lands on the red days, which are the days the question exists for.

## v3.147 — the command beside the number

`v3.146` closed `O-128` and opened `O-131` with a mechanism: *the bound is looked up by step name*. The entry
was right that something crossed two trees and wrong about what. Both sides of that comparison come from that
day, so the bound *was* the bound of the step whose seconds were being read; what crossed the trees was the
**command**, and it crossed in the one place nobody was looking -- the field written beside the number.

### A reading is a pair, and only the recorder could keep it a pair

`R10` divides a bound by the slowest reading **of the command the bound bounds**, which is why the history
stores a command with every number (`commands[name] = commandOf(step)`) rather than a step name. The gate never
reads that command: it only divides. So the pair can only be broken by the recorder, and it was, on both paths:

| the path | where the number came from | where the command came from |
| --- | --- | --- |
| a seed | that day's report, looked up by step **name** | **today's** `ci.yml`, by the same name |
| a recording | the run's report | **whatever was on disk**, never compared with the run's commit |

A name is a label, and a label survives a change of the line under it -- the ordinary way a workflow moves.
